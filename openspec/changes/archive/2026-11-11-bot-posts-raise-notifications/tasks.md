## 1. Notification records with a bot owner

- [x] 1.1 In `packages/server-core/src/notifications/types.ts`, make `NotificationRecord` and `NotificationEvent` discriminated unions on `owner` (`'terminal'` with required `projectId`/`sessionId`; `'bot'` with required `botId`, `count`, `throughSequence`, `source: 'bot'`, `kind: 'bot-message'`). Every event carries `owner` and its identity at the top level, removals included. Mirror the change in `packages/client-core/src/notifications.ts`, whose parser treats a record without `owner` as a terminal record and rejects mixed identities. Verified by `npm run typecheck`, and by client-core parser tests for a legacy terminal record, a bot record, and rejected mixed or incomplete records.
- [x] 1.2 Add `NotificationManager.setBot(botId, { count, body, raisedAt, throughSequence } | undefined)`. It keeps one record per bot, keeps id and publication state on change, emits `notification.changed` without restarting the settle period once published, and removes the record on `undefined`. Verified by new cases in `packages/server-core/test/notification-manager.test.mjs`: one withdrawn inside the settle period is never published; an update while pending keeps the original settle deadline; an update while published emits `changed` with the same id; `undefined` emits `removed` carrying `owner: 'bot'` and `botId`.
- [x] 1.3 Replace the project-claim argument of `snapshot`/`replay` with a visibility filter `{ projectId?, bots }` that omits bot records and every bot event, removals included, when `bots` is false or a project is claimed. Verified by manager tests showing a bot record and its removal hidden from a project-claimed and a `bots: false` snapshot and replay, while revisions stay global.

## 2. Notification protocol boundary

- [x] 2.1 In `notifications/protocol.ts`, compute `bots` with `canReadBotEvents` for snapshot and delta, and drop bot events in `createNotificationEventProjector` by their top-level `owner` unless the client has bot authority and no project claim. Verified by `packages/server-core/test/notification-protocol.test.mjs` cases for a read-scope client, a project-claimed client, a session- or capability-claimed client, and a write-scope client, across published, changed, and removed events, live and in replay. Only the write-scope client receives any of them.
- [x] 2.2 Accept a dismissal payload with either `projectId`+`sessionId` or `botId`, and reject one with both or neither as `validation`. A `botId` dismissal requires bot authority and calls `acknowledgeBot(botId, record.throughSequence)`. Verified by protocol tests: a mixed payload is rejected; a dismissal without bot authority is `forbidden` and changes nothing; an authorized dismissal acknowledges through the record's sequence; a post stored after the record's sequence survives the dismissal.
- [x] 2.3 Make `automationSpaceVisibility` pass bot records and events through untouched. Verified by a unit test feeding a snapshot and a delta with bot records through `withholdNotificationSnapshot` and the delta projector.

## 3. Bot acknowledgement and feed

- [x] 3.1 Add a persisted `acknowledgedSequence` to `BotMessageStore` state. When missing, it defaults to the current `sequence`. Add `acknowledge(botId, throughSequence)`, which is monotonic, clamped to `sequence`, and writes nothing when there is no advance. Make a user `post` acknowledge through its own sequence. Verified by bot message store tests covering default-on-load, monotonicity under a stale value, clamping, a no-op without a write, a user post acknowledging, and the value surviving a store reload.
- [x] 3.2 Add `BotNotificationFeed` in `botService/`. It derives `{ count, body, raisedAt, throughSequence }` from bot posts after the acknowledged sequence, with an excerpt of ≤280 characters, or `Sent an image` for an attachments-only post. It recomputes on post, edit, remove, clear, and acknowledge, removes the record on bot deletion, and restores every bot at startup. Verified by unit tests for one post, three posts, editing the latest post, deleting the latest, deleting the only post, clearing and then posting again, an attachments-only post, bot removal, acknowledgement racing a newer post, and restart restoration with and without acknowledgement.
- [x] 3.3 Add the `bots.messages.acknowledge { botId, throughSequence }` command to `BOT_MESSAGE_OPERATIONS` and `messageProtocol.ts` behind `assertBotAuthority`, and add it to the client-core bot messages client. Verified by a protocol test showing an MCP or project-claimed caller refused and an authorized caller advancing the sequence.
- [x] 3.4 Wire the feed and `acknowledgeBot` into the server composition, so the notification registry dismisses through the bot service. Verified by a server-core composition test showing a bot post publishing a record after the settle period, and a `notifications.dismiss` with `botId` removing it.
