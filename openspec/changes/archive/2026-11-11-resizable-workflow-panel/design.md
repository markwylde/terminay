## Context

`WorkflowPanel` renders inside a terminal pane (ADR-0097). `TerminalPanel` reserves `reservedWidth(mode)` pixels of right padding, so xterm fits what is left, and computes `columnsBesideRail` and `cellWidth` after each fit. `panelMode(setting, columnsBesideRail, cellWidth)` returns `forced-collapsed` when the terminal would drop below 60 columns beside the fixed 264px panel. The collapse choice lives in `workflowPanelSetting.ts`, a `useSyncExternalStore` store over `localStorage` key `terminay.workflowPanel.v1`, which also follows other windows through the `storage` event.

The workspace column widths (Folders, project sidebar, Home) are device-remembered in `localViewState.ts` and resized by `useTrackResize` in `WorkspaceSplitLayout.tsx`: a pointer drag previews live, commits once on pointer-up, cancels on `pointercancel` or window blur, keeps the gesture through window listeners when pointer capture is lost, and Arrow keys step by 16px. During that preview the content column narrows with the pointer, so terminals in it refit as it moves.

## Goals / Non-Goals

**Goals:** a draggable and keyboard-operable width for the expanded workflow panel; one chosen width shared by every terminal that reads the same device storage; the terminal never covered by the panel and never below 60 columns.

**Non-Goals:** no resizing of the collapsed rail (it is a fixed 36px marker strip); no per-terminal or per-project width; no server, protocol or template change; no double-click reset; no new host preference channel to share the width across server connection profiles.

## Decisions

- **Chosen width and effective width.** The *chosen width* is the user's setting. The *effective width* is what one pane draws: `panelLayout(setting, chosenWidth, columnsBesideRail, cellWidth)` in `workflowPanelModel.ts` returns `{ mode, width, maxWidth }`. When expanded, `width` is the chosen width reduced to `maxWidth`, the widest width that keeps the terminal at 60 columns (capped at 640). When `maxWidth` is below the 200px minimum, the mode is `forced-collapsed`. Without geometry yet (before the first fit), `width` is the chosen width and `maxWidth` is 640. Panes are constrained independently, so two panes can draw different effective widths from one chosen width. `reservedWidth(layout)` returns the effective width when expanded and the rail's 36px otherwise.
- **Live preview that never covers the terminal.** Codex flagged that a CSS-only preview would draw the widening panel over terminal output, against "Workflow panel in the terminal pane". So the preview is pane state: `TerminalPanel` holds a `previewWidth`, `WorkflowPanel` reports it through `onPreviewWidth(width | null)`, and the layout uses `previewWidth ?? chosenWidth`. The pane's padding follows the preview, and the terminal refits through the existing rAF-throttled fit, as terminals do while the workspace sidebar is dragged. Release commits once through `setWorkflowPanelWidth` and clears the preview. Alternative considered: a guide line during drag and one refit on release. Rejected as inconsistent with the workspace separators, which resize live.
- **Gesture origin and commit rules.** A gesture starts from the pane's effective width, not the chosen width, so the panel never jumps under the pointer. A pointer gesture that never moves commits nothing, so clicking the separator of a narrowed panel does not replace a larger chosen width. A gesture that moves commits its final width, which becomes the chosen width. Arrow Left and Arrow Right step the effective width by 16px within `[200, maxWidth]` and commit. A `pointercancel`, a window blur, or unmounting mid-drag clears the preview and commits nothing, so the panel and terminal return to their earlier widths. Pointer capture loss does not end the gesture; window listeners keep it, as in `useTrackResize`.
- **Store the width beside the collapse setting.** `useRememberedColumnWidth` keeps a React state per hook instance and only follows *other* windows. Every terminal pane mounts its own panel, so a resize in one pane must reach the others in the same window immediately. `workflowPanelSetting.ts` already has an in-memory module value with listeners plus a `storage` listener. A second store in that module, key `terminay.workflowPanelWidth.v1`, gets the same behaviour. Reading: a stored safe integer in `[200, 640]` is used; anything else (missing, garbage, out of range) reads as 264. Writing: the setter rounds and clamps to `[200, 640]`, and storage failure is silent. Alternative considered: add `workflow` to `ResizableColumn`. Rejected because that store's 30–2000 bounds and per-instance state do not fit.
- **Scope of "device".** Under ADR-0005 the desktop host gives each server connection profile its own storage partition, so windows of the same server share the width and windows of different servers do not. That is already the scope of the collapse setting and the workspace column widths; the spec states it the same way, as a device-local setting per server.
- **Measure the real cell width.** The pane used to estimate a cell as `root.clientWidth / cols`, which folds the fit's leftover pixels and the scrollbar into the cell. With a fixed panel that error was constant; with a variable panel it moves the pane's maximum after every refit, so the panel never settles (found by the split-pane E2E). The pane now uses `terminal.dimensions.css.cell.width` and subtracts the fit addon's own overhead (element padding plus scrollbar width, as `FitAddon.proposeDimensions` computes it) before counting columns.
- **Bounds.** Minimum 200px (the header's name, count, elapsed time and collapse button still fit). Maximum 640px. Default 264px, the current width.
- **Overlay width.** The narrow-pane overlay uses `min(chosenWidth, 85% of the pane)`, so it stays usable in a narrow pane, and `WorkflowPanel` takes the chosen width as its own prop for this. It has no separator: it is transient and must not change a setting. It reserves nothing, so it never resizes the terminal.
- **Separator.** An `<hr>` with `role="separator"`, `tabIndex={0}`, `aria-orientation="vertical"`, `aria-label="Resize workflow panel"`, `aria-valuemin={200}`, `aria-valuemax={maxWidth}`, and `aria-valuenow` the effective width. It sits on the expanded panel's left edge, 6px wide, styled like the workspace separators. Alternative considered: export `useTrackResize`. Rejected because it is bound to the layout root's CSS variable and its controlled/uncontrolled props; extracting it would touch the workspace layout for no user gain.
- **Boundary.** Presentation only, in the server-bundled workspace UI. The width never leaves the device's storage partition and grants nothing; the project/window and terminal-session boundaries are untouched.

## Risks / Trade-offs

- Live preview resizes the PTY during the drag. The fit is already rAF-throttled and only sends a resize when columns change, the same cost as dragging the workspace sidebar.
- Two panes can show different effective widths from one chosen width. This is intended: the guarantee is the terminal's 60 columns, and the chosen width is an upper bound.
